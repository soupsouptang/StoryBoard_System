## 3. 架构与扩展准入

唯一运行目标是 apps/web、apps/api、apps/worker；PostgreSQL 保存持久事实，Alembic 管理数据库结构历史，Redis 保存临时在线协作和编辑租约，存储适配器管理媒体。Node.js 24、Python 3.12；具体依赖以实际锁文件和已接受升级为准。

根共享包保持 packages/ui、packages/types、packages/contracts、packages/timecode。新增模块留在应用内，不新增万能 common、core 或 shared 包，不为目录整齐搬动已接受服务。

新增能力先判断它是独立对象、对象字段、两个对象的明确连接、工作流、视图还是解析与渲染服务。真实对象分别保存事实，看板、通告草稿和统计从事实查询；不得为导演、摄影和制片复制三套镜头。

新对象或字段必须写清使用者、操作、数据负责人、输入输出、权限、版本检查、事务、历史、事件、引用、删除、导入导出、迁移及真实验收。缺项只暂停该模块；空页面、空接口和模型文件不能充当实现。

优先复用成熟库和现有服务。禁止覆盖全系统的万能实体或关系表、全部数据塞 JSON、任意脚本规则、运行时用户代码插件、服务互改对方表、人工智能直接写库，以及前端多个请求拼假原子保存。

### 3.1 Entity从属关系的判定

一级对象可以拥有真正从属的子对象，父子关系必须表达明确所有权、生命周期和作用域。业务上有关联不足以建立父子层级；独立对象通过有明确类型的关系连接。不能用含糊的“默认不挂镜头”代替判断。

| 关系 | 所有权与删除行为 |
| --- | --- |
| 项目拥有镜头、场景、项目现实人员 | 项目范围内独立身份；删一个场景不删除关联镜头 |
| 镜头拥有分镜面板 | 面板不单独迁往另一镜头；永久删除按引用清理，不自动删共享原图 |
| 素材拥有版本，版本拥有物理组件 | 版本不可变；正式引用期间保留，共享物理文件按引用处理 |
| Work拥有Episode | 组织生命周期明确；关联项目独立，删容器先处理关系，不能连带销毁项目 |
| 任务拥有输入和产物绑定记录 | 绑定随任务处理，原素材、镜头和人员不属于任务 |
| 需求关联时间安排和知识型号 | 明确关联来源、时间及型号；汇总是可重建查询，不建立库存所有权 |
| 场景与镜头、人员与角色、任务与素材 | 独立对象的业务连接，不是父子 |

新增关系如所有权、独立性、恢复或删除行为不清楚，先向用户确认；不能靠名称或页面位置推断。

## 4. 项目组织、身份与权限

项目是独立工作区，拥有篇章、场景、镜头、素材、现实人员、任务、排期、审阅及交付事实；拥有资源需求和使用配置，通过明确关系连接时间安排及型号参考，不建立大库房。

归组和移动不复制项目、不改变镜头身份、版本、媒体引用或成员权限。独立项目无需填写空系列。上层计数、摘要和批量操作逐项目授权；多个独立事务要分别返回结果，不能冒称全部原子成功。

现实人员在项目内独立，可没有账号。姓名不唯一，不按姓名或邮箱自动匹配；账号停用、解绑不删除人员和已经发生的执行。剧情角色、选角候选和确定演员分开；工作人员通过任职和任务关系参与。

实现细化：同一项目一个人员最多一个当前账号关联，一个账号最多一个当前人员关联；跨项目各有人员身份。改变此基数须新的明确需求，不偷偷改约束。

岗位和工种决定职责及视图，不自动授予项目权限。项目授权、用户组、明确拒绝和对象字段策略由统一权限服务处理。用户管理与项目正文访问分开。库房已取消，资源查询沿原项目授权，没有岗位或库房资格例外。

列表、计数、详情、历史、撤销、媒体、分享、导出、实时连接和异步结果发布都检查同一有效权限。授权变化使缓存、连接和未完成结果重新校验。审片链接限制范围、期限、字段、固定媒体、下载和评论；到期或撤销后阻断访问。

项目标题、帧率、分享状态在现有独立项目设置页编辑，不恢复旧设置弹窗。

项目修改帧率时自动保留镜头秒数并重新计算帧数，不让用户在两套策略之间选择。使用统一分数帧率工具计算，整数帧采用一致舍入规则，正时长至少一帧；预览逐镜头与总时长、起止时码的舍入差异，保存为一条原子命令。锁定时长保留其秒数；实际语音音频长度和拍摄排期的真实时间不随帧率改变。

## 5. 场景、镜头与演职人员

场景和镜头多对多，两端校验同项目；活动连接不重复，同镜头最多一个主场景。首版连接类型使用 related，主场景单独标记；叙事备注不触发自动业务行为。

全局镜头和片长按镜头身份去重，场景引用数单列。场景顺序、全局镜头顺序、镜头篇章与拍摄次数不是同一件事。导入、导出、排期和视图保留多关系。

演员、场地、设备的有效要求由当前场景要求和镜头手动覆盖计算。记录稳定来源身份和版本；场景变动影响未覆盖项及有关未来任务输入，不改已完成实际记录。恢复继承取当前来源；来源永久删除后新建的同名项不能套用旧覆盖。

要求不是实际出演、器材已经具备或实际使用。实际出现分画内、声音、背景、替身等明确类型，角色未选演员不冒充确定人员。需求识别见资源方案，数量按 D-28 计算，不产生库存或预留。

环境显示遵循镜头明确值、主场景值和差异提示。明确空值与没有覆盖分开。对白先保留原文本和明确角色引用；只有真实多说话人编辑或字幕入口需要时再引入结构化对白段落，不预建空表。

## 6. 字段、列与共享视图

复用现有字段负责人，按实际实体增加字段范围。稳定定义身份用于引用，同项目、同实体范围、同字段键唯一。已绑定核心值或真实关系的字段不另存一套自定义值。

自定义值按镜头、场景等真实对象建立有明确外键的值记录。数值零、布尔假、空值和未提供分开；非法类型拒绝，不截断或静默回填。默认值不改已有历史；类型转换先预览失败行，再检查版本并原子保存。

计算字段只读，使用有限表达式支持算术、条件、舍入、空值处理、比较和允许的同对象字段及帧率。拒绝依赖环、任意脚本、网络和跨项目查询。除零、缺值和类型错误有明确状态，不当成零。

| 操作 | 结果 |
| --- | --- |
| 隐藏 | 改共享视图显示，不删定义和数据 |
| 删除 | 进入回收站，保留值和历史，同身份恢复 |
| 永久删除 | 仅预设、自定义项目实例，确认影响后清当前值及受控历史正文 |
| 重新添加 | 内置恢复原身份；已永久删除的预设、自定义新建身份，不能复活旧值 |

新项目显示镜号、分镜画面、时码、时长、镜头标题、篇章、画面描述、制作方式、状态九列。二十个预设列按需启用，未知导入列可建自定义并保留来源。未接通的预设保持待映射，不能用自由文本冒充真实关系。

共享视图配置由 SavedView 唯一保存，包括列显示、顺序、宽度、行高、筛选、排序、分组、换行和自动尺寸。WorkspaceLayout 只保存个人面板、所选视图等个人偏好，不重复保存权威列布局。评论列没有可见审阅标记时隐藏，不删除审阅历史。

成员可选择不同视图；进入同一视图的人同步其配置，个人选择、光标和草稿独立。拖动本地预览，确认后检查配置版本，服务器保存后广播；冲突保留草稿，重连读取权威配置。

支持手动列宽、行高和自动模式，没有自定义列高。自动模式保存稳定测量规则及结果版本，不按每个人窗口各写一份尺寸；沿已接受界面尺寸，不能借自动测量重做工作台。布局不改变创作内容版本。

## 7. 工种工作流、任务与看板

制作步骤表达镜头工艺，任务表达独立执行。模板固定版本，实例固定所用版本，升级不重写在途任务。支持用户建立节点与依赖，不因没有默认模板暂停基础功能。

任务保存主责、协作、部门、输入产物、计划与实际用时、明确目标和修订。草稿可未派人，开始前必须有主责和必需输入；提交和交接固定素材版本。完成、取消、跳过、返工、更正分开，独立审片禁止自确认。

首版依赖是前项完成后后项可开始，同项目、非自身、重复边拒绝。并发加边要锁定受影响依赖图后验环。可开始、受阻和输入过期由事实计算；共享场景任务只执行一次。

摄影、灯光、制片、演员、剪辑、声音和审阅看同一事实的授权查询。指标写清分母、状态、去重单位和下钻对象；重叠制作方式不相加冒充镜头数，取消排除、过期单列、零分母不显示百分之百。不未经新决定替换原四项概览。


### 7.1 Scene / Shot 到实际 Task 的闭环

Scene、Shot、制作方式和项目模板只是工作需求来源，不能把“选择了制作方式”当成“任务已经执行”。系统必须把可复用工作流实例化为真实 Task，再由 Task 承担负责人、计划、实际、输入、产物、交接和执行历史。

首次实例化至少支持以下来源：

- 项目模板提供默认阶段、任务节点和依赖；
- Scene Requirement、Shot override 和 Production Method 增加或移除适用任务；
- 用户可以在不套模板时明确创建 Task 和依赖；
- 同一共享 Scene 准备只生成一项真实 Task，再通过 typed link 服务多个 Shot，不能复制 N 个“完成状态”；
- 重复应用同一模板或同一自动化来源必须幂等，不重复生成任务。

任务默认执行流为“待安排 → 可开始 → 进行中 → 待交接 → 已完成”，取消与跳过是明确动作；blocked、overdue、input stale 是可并存的派生标记，不替代真实阶段。开始条件来自固定输入、前置依赖、人员和必要准备，不以页面是否打开判断。

任务适用性必须随其来源重新计算。Scene、Shot、Production Method、Requirement 或 WorkflowTemplate 的变化使某个自动生成 Task 不再适用时，只有同时满足“系统自动生成、未开始、无 Actual、无输出产物、无交接事实”的 Task 才允许自动进入“不再需要/停用”状态；该状态与人工 Cancel 分开，不计为用户主动取消。已经开始、已经提交/交接、已有输出，或由用户手动创建的 Task 保留其事实、依赖和历史，系统只标记来源已失效/需负责人处理，不自动删除或取消。若同一稳定来源重新变为适用，尚未执行且未产生事实的自动停用 Task 可以在保留历史的前提下恢复适用；已经执行过的旧 Task 不复活为新的执行事实。

Task 的完成不能直接把 Shot、Review 或 Deliverable 写成完成。Task 提交固定输出版本；需要交接时由接收方确认固定 AssetVersion 或明确缺项。输入后来变化，只使相关下游标记过期或返工，不抹去“当时已经完成和交接”的事实。

“我的工作”、部门看板和项目任务视图均查询同一 Task owner。一个 Person 多工种仍是同一现实人员；不同岗位视图不能复制任务正文。未分派、未知工时、缺输入、待交接和冲突必须可单独查询，确保任务可以从 Scene/Shot 真正流向人员执行，而不是停在镜头字段。

## 8. 时间段资源需求与排期

最新范围见[资源需求方案](RESOURCE_TIME_REQUIREMENTS_2026-10-04.md)。第15问明确取消通用大库房，只保留知识参考和时间段需要什么。没有库存登记、项目数量配额、真实预留、领用审批或库房资格。

场景要求、镜头逐项覆盖和导入字段提供需求来源；同一时段独立需求相加，明确共用只计一次，不同时段分别计算。缺数量、型号或时间分别提示未知，未排期不猜时段。需求汇总不宣称资源已具备，也不与库存比较。器材知识仅保留型号和基础知识，去掉使用方法。需求与既有排期关联，未排期另列；人员与场地继续由原排期模块管理，不另建重复名单。

排期存储UTC及项目时区，使用前闭后开区间，默认北京时间，可改偏好或新项目默认。个人显示偏好不移动时间；改项目时区先预览。夏令时重复或不存在时刻明确偏移，不猜。

工作休息窗口、拍摄日分界和实际时间通过配置提供。方案分草稿、当前和被替代修订；同项目及明确摄制组范围最多一个当前方案。一个镜头可以跨日、多摄制组和补拍，片长不是拍摄时段。准备、拍摄、排练、转场和休息明确类型，不重复累计。

人员和场地的跨项目冲突继续依据明确共享身份及受权摘要；不按姓名合并。没有资料显示未知，锁定项不自动解锁。通告发布固定来源和接收范围；正常联动更新可推导未来安排，例外说明原因、负责人和重试，不改变实际执行和旧发布事实。



### 8.1 排期的事实来源与边界

排期不是 Scene 或 Shot 的日期字段副本。SchedulePlan 是方案 owner；ShootDay 和 ScheduleItem 表达某一方案中真实的时间区间。Scene、Shot、Task、Person、Location、资源需求通过 typed link 进入 ScheduleItem，一个镜头可以出现在多个排期条目中用于跨日、补拍或不同摄制组，不改变镜头本身的内容身份。

ScheduleItem 至少区分准备、妆发/试装、排练、拍摄、休息、转场、撤收等业务类型。预计时长、实际开始/结束和实际结果分开；镜头成片时长不作为拍摄工时。未排期的工作继续存在于待安排队列，不因没有日期而丢失。

SchedulePlan 支持多个草案方案比较，但同一 Production / Unit scope 最多一个 CURRENT。切换 CURRENT 必须原子检查修订；未选中的方案不能驱动当前通告、人员时间线或后期预测。锁定条目、锁定时间窗和人工 override 不被自动重排偷偷覆盖，冲突转入例外。

### 8.2 演职人员排期闭环

Person 的 Availability、项目任职、CastAssignment、TaskAssignee 和 ScheduleItemPerson 分别表达“能不能来”“在项目中做什么”“饰演谁”“负责什么任务”和“某时段实际被安排什么”，不能合并成一个状态。

演员时间线应覆盖适用的试装、妆发、排练、旅行、待命、拍摄、配音/补录和释放；工作人员时间线覆盖准备、Setup、拍摄、撤收、转场和交接。一个现实人员同时兼任多个岗位，只占用同一条 Person 时间线，不按 Role 数重复计算人。

档期缺失是 UNKNOWN，不当作全天可用；TENTATIVE、AVAILABLE、UNAVAILABLE 分开。跨午夜和项目时区按实际区间判断。排期查询必须能从一个 Person 反查关联 Scene、Shot、Task、ShootDay 和 CallSheetRevision，也能从 Scene/Shot 找到所需人员及当前冲突。

人员变更或场景出演关系变化后，系统重算未锁定的未来安排、个人时间线和当前通告草稿；已发生的到场、工作和旧通告确认不被改写。无法成立的安排显示冲突对象、时间、原因和待处理负责人，不自动换演员或替用户作创作决定。

### 8.3 拍摄排期与方案比较

拍摄排期把 Scene/Shot 的内容关系、Task readiness、人员/场地可用性、时间段器材/道具需求、项目工作窗口和明确锁定条件合并为可解释的约束。硬约束不能被优化器违反；软目标只能作为排序/建议依据，未配置优化优先级时只做冲突检测和人工排序，不擅自宣称“全局最优”。

一个拍摄条目的预计区间可由准备、Setup、排练、Shoot、Reset、Strike 等组成；共享场景准备只计算一次。系统允许按 Scene 先排，再展开具体 Shot；也允许明确按 Shot 排。排期方案比较至少能显示拍摄天数、人员冲突、场地冲突、转场数量/时长、锁定冲突、未排工作和后期可开始时间，不能用单一“得分”隐藏不可行条件。

任何自动重排只修改未来未锁定计划。实际开始/结束、已完成工作、已发布旧通告、已交接产物和旧基准保留。用户应能看出“系统算出的时间”“人工锁定时间”和“手动 override”三种来源。

### 8.4 Company Move / 转场闭环

转场是排期中的正式 ScheduleItem 类型，不建立与 SchedulePlan 平行的第二套时间轴。它连接前后拍摄条目和 From / To Location，并保存用于排期的撤收、装载、行驶、卸载、Setup 等组成时长；这些组成只服务该转场的计划和实际，不成为新的一级业务对象。

前一拍摄条目结束后，下一场最早可开始时间必须考虑适用的 Strike、Load、Travel、Unload、Setup，而不是只使用地图行驶时间。人员、器材和车辆如有不同移动路径，通过各自 ScheduleItem / typed link 表达；需要先行组时明确创建先行安排，不把整组强制复制到所有人。

上游延误、地点变化或转场时间修订会重算之后未锁定条目；若下一场地窗口、演员窗口或锁定开拍时间无法满足，形成明确冲突。实际转场时间回写后参与当天剩余计划预测和经验校准。

### 8.5 每日计划与通告闭环

Call Sheet Draft 是 CURRENT SchedulePlan、ShootDay、Scene/Shot、Person、Location 和当日准备事实的授权投影，不是另一套手工维护的数据。正式发布时生成不可变 CallSheetRevision，固定来源 revision vector、接收人范围、个人集合时间、地点、场次/镜头、特殊准备和允许字段。

生成、发布、通知送达、打开查看、个人确认、现场到场和工作完成是不同事实。重要时间或地点变化发布新 revision 后，旧确认仍绑定旧 revision，需要时明确进入重新确认；普通未来计划联动不等待所有人先确认才继续更新。

不同人员可以有不同 Call Time；演员妆发、工作人员 Setup、摄影开机和车辆集合不能默认使用同一时间。CallSheetRevision 可以被撤回或被新 revision 取代，但旧发布内容和当时确认保留历史，不能随当前排期静默漂移。

排期、人员、地点或集合要求变化后，系统只自动重算当前 Call Sheet Draft、标出与最近已发布 revision 的差异，并精确标记哪些 Recipient 因重要时间/地点/集合要求改变而需要重新确认。系统不得因为草稿已更新就自动生成“已发布”事实，也不得自动把新版外发。只有具有发布权限的人显式 Publish 才创建新的不可变 CallSheetRevision；只有具有发送权限并明确执行 Send/Notify 时才产生外发记录。发布与发送是两个动作，允许先发布后不发送。

### 8.6 当天执行与动态重排

ShootDay 开始后，ScheduleItem 记录实际开始、实际结束、执行状态、延误/提前和明确更正。系统使用 Actual 与剩余 Planned 区间持续计算当天剩余时间、预计 Wrap 和后续转场，不把 Actual 反写成原计划或 Baseline。

若某条拍摄实际超时，系统自动重算后续未锁定条目的可行时间并显示影响。超出场地窗口、演员窗口、工作休息限制或当日可用时段时进入例外；系统可以给出移动到后续 ShootDay、调整顺序或保留冲突的候选操作，但不自动删除镜头或替导演决定取消。

现场“已执行 ScheduleItem”不等于 Shot 已满足全部拍摄要求。Shot 可以明确为已满足、部分满足、未满足或产生补拍需求；在 Take 尚未启用期间，用 ScheduleItem 实际事实 + Shot 完成/补拍事实 + Media 交接连接现场和后期，不制造空白 Take。

### 8.7 排期到后期输入的预测

后期计划不等全部拍完才开始。每个需要素材输入的 Task 根据关联 ShootDay / ScheduleItem、预计媒体可用时间和已完成的 MediaHandoff 计算 earliest start。拍摄排期变化自动刷新未来剪辑、AE、UE/3D、声音、调色、Review 和 Delivery 的预测日期；固定交付目标本身不被内部改期偷偷移动。

没有收到固定输入版本时，后期 Task 显示 blocked 或 input pending；计划日期可以存在，但不能冒充“已经可开始”。实际素材交接完成后，预测切换为事实驱动，相关 Task 重新计算 readiness。


## 9. 创作版本、独立历史与撤销重做

| 数据 | 项目创作版本 | 其他记录 |
| --- | --- | --- |
| 镜头、场景、篇章、多场景连接、字段值、面板构图、灯光 | 进入 | 普通内容命令可撤销 |
| 剧情角色、选角、场景要求、镜头出演 | 进入 | 不复制人员私人档案 |

| 批注和审阅 | 不进入 | 固定受审内容、媒体版本和自己的修订 |
| 任务实际、交接、通告发布 | 不进入 | 显式更正或撤回，不抹去已经发生的事实 |
| 共享视图、个人布局、导出配置、情绪板 | 不进入 | 可撤销操作复用原项目历史；情绪板仍可撤销 |
| 资源要求、时间段汇总 | 要求按所属创作对象固定，排期不进入 | 查询汇总可重建，普通需求命令复用原历史；不设库房历史 |

项目提交固定创作集合、作者、时间、消息、父提交和内容校验。类 Git 显示新增、修改、删除、未变、并排文本和固定构图版本图片；镜头比较只是筛选项目差异，不建第二套镜头提交。

恢复和三方合并先预览身份、当前与目标版本、依赖和永久删除缺项，再原子命令生成新版本。不同非空冲突明确解决；未知格式不能跳过冒称成功。不恢复权限、批准或已执行事实；本方案不再包含库存和预留。

HistoryService 是唯一项目持久命令历史，用户加项目最近一百步，刷新保留，复合操作一条。服务端生成补偿内容；每个模块声明恢复、权限、引用、顺序、版本和永久删除策略，不反射整个数据库。

撤销重做是新的补偿命令，重验当前权限、修订和引用；冲突整步不写、不移动游标，成功修订继续递增。新命令清本人的重做分支；不能擦掉他人后来修改。输入法、文本和裁剪草稿使用本地撤销，不抢项目快捷键。

永久删除、不可逆外发和权限敏感操作不进入普通撤销。2D/3D对象内容进版本，相机导航、缩放和选择只是显示。所有需求按真实项目作用域进入原历史，不创建已取消的库房游标。

## 10. 命令、查询与并发

写入由统一身份和权限检查进入域命令，检查所需修订，再同事务保存业务、审计、适用历史、事务事件和请求回执。路由负责请求、格式和错误映射，不直接编排跨模块数据库业务。

新命令有稳定请求身份、格式版本、有效载荷和依赖修订；操作者、权限、补偿和修订递增由服务端生成。同请求同内容重试一次生效，不同内容复用身份返回冲突。重放成功回执仍检查当前权限及永久删除，不因旧预期修订变化误报失败。

无实际变化可以留最小技术回执，但不改更新时间、业务修订、审计、历史或事件。只有事务提交后才能显示已保存。客户端区分未保存、保存中、已确认、失败和冲突，刷新不覆盖草稿，冲突不盲重试。

项目命令按项目根、对象的稳定身份顺序锁定；跨项目组织操作明确逐项目回执，不伪装全项目原子成功。取消库存后不引入全站库存锁，需求查询基于明确来源修订和时间范围。

查询在数据库或授权投影阶段过滤对象、字段和计数，返回稳定分页、来源版本、查询时间及计算口径。缓存包含权限范围、条件、内容或配置版本及删除版本；缓存和 Redis 失效不丢正文。

沿现有错误格式解释未登录、无权限、不存在、冲突、非法输入或暂时不可用，并给下一步。保留草稿，不展示数据库语句、堆栈和凭据，不写免责声明。需求缺值、未排期和语义冲突分别提示，不伪造资源充足状态。

## 11. 导入、文字识别与来源

复用 ImportService，解析器按 Excel、CSV、Word、PDF、图片和便携工程划分，采用成熟库。解析结果与合并决策分开，资源需求消费已有结果，不再写另一套PDF或Excel解析器。

每次按内容识别，不保存客户或导演长期导入模板。保留表头、原列、源行页、嵌图、单位、时间码和置信状态；高置信预选仍进预览，同名关系不静默绑定。未知列可建自定义，不能覆盖内部身份。

多个源列映射同字段，按类型处理相同和空值；不同非空默认冲突。文本只有明确策略才拼接；零和假有效。添加、更新覆盖、替换都先预览，替换明确删除范围，不清整个项目或其他模块。

冻结导入计划固定文件校验、解析器和目录版本、映射、字段决定、目标身份及修订、权限与删除状态、媒体清单。执行不重新猜映射；源或目标变化重新预览，最后一行或图片失败也整步回滚。

正式来源保存识别、映射、合并和目标来源版本；临时预览和正式来源分别留存。二次导入按来源或用户确认匹配，不用镜号当稳定身份。文字识别可核对原图和文本，识别失败明确显示，不编造数量。旧版仅保留便携工程文件映射桥，不迁旧数据库或兼容旧接口。

## 12. 资产图片、画板与旁白

素材独立于镜头附件，可由面板、场景、任务、审阅和画板引用。原图和素材版本不可变；原件、代理、预览、缩略图是同版本组件，不各建作品版本。

资产库支持上传、命名分类、搜索、引用明细、删除恢复、裁剪重框选和下载。共用构图服务；资产库支持横竖、21:9、16:9、自定义比例、旋转翻转，不拉伸，适配后填黑。资产默认构图更新只影响没有专用构图的当前引用；镜头面板、项目封面的专用构图保持。创作提交、审片和交付固定当时的有效构图及其版本，不能随资产默认值漂移，恢复旧提交也不反向更改全局资产默认值。

已有镜头图片预览遵循最新明确界面：固定项目画幅，胶囊缩放控件、拖动、锁定、本地草稿撤销和整卡保存；不把资产库自由比例控件重新塞进镜头弹窗。新上传默认铺满；“载入原图”按完整原图适配、居中填黑，均不改原字节。缩略图异步生成，失败可重试；建立项目时和之后可改竖版，分镜图框随项目比例改变，入口封面仍保持横向整行。

灯光2D、3D和分屏共用同一对象数据与映射，选中、移动、旋转、参数、保存冲突和撤销完整。型号参考与画板中的设备需求分别处理，不将视觉模型当作已验证工程光学精度。

情绪板支持图片、便签、色卡、链接、排序移动、关联镜头、权限、素材引用和撤销；不进创作版本，仍检查数据和删除。拖动过程本地预览，不每帧持久写入。

旁白区分预计朗读、锁定时长和实际语音合成音频。语速滑杆和可播放样例共用真实服务与异步任务，拖动不每帧请求；按文本、语言、声音、速度和服务版本缓存。没有真实输出明确不可用，不能提供假播放。



### 12.1 现场结果、素材检查与后期交接闭环

现场完成的 ScheduleItem 可以产生或关联 MediaAsset / AssetVersion；素材身份必须能追溯到 Production、ShootDay、ScheduleItem、Scene/Shot 和产生它的任务/来源。没有 Take 的首版不强制人为创建条次对象，但未来启用 Take 时通过 typed relation 增加粒度，不能改写已有素材身份。

“文件上传成功”“完整性检查通过”“备份验证完成”“可查看代理生成”“已交接给后期”必须是不同事实。原素材、代理、预览和缩略图仍是同一 AssetVersion 的不同组件；固定交接必须引用明确 AssetVersion，不能引用会随当前版本漂移的“最新文件”。

正式素材交接采用 D-37：AssetVersion 必须先通过完整性检查，并满足该项目当前配置要求的全部 BackupVerification 条件，才可产生 Formal Handoff / 正式接收事实。项目没有配置某类额外备份要求时不凭行业习惯自行增加隐藏门槛，但完整性检查始终是正式交接的基础条件。备份尚未满足时可以生成或开放明确标记为 Preview / PREPROCESS_ONLY 的代理或预览，供剪辑、AE、声音等做草稿预处理；这种访问不能将正式输入标记为 Ready，也不能被最终输出、正式 Review 或 Delivery 当作已交接依据。

首版若一次交接只服务一项 Task，可由 TaskAssetVersion + 接收事实表达；当同一素材需要多消费者、独立确认、撤回/更正或单独权限时，MediaHandoff 才成为独立 Entity。引入 MediaHandoff 前必须按 §3.1 说明其 owner、生命周期、权限、revision、历史、自动化和 typed relations，不建立万能 handoff JSON。

后期接收方看到的状态至少区分：缺输入、待检查、检查失败、待备份验证、可使用、已交接、输入已过期。素材后来被替换或上游 Shot 产生补拍时，只影响引用了相关输入的下游 Task；已经完成的旧版本和旧交接保留，必要时生成返工需求。


## 13. 导出、工程码、水印与分享

同一授权投影供预览、正文、附件、工程数据和便携包；格式服务只渲染，不另持写权限。导出配置固定格式、范围、字段顺序、布局、纸张方向、图片比例质量、页眉页脚、水印和文件名，不被当前可见列隐式代替。

覆盖横竖分镜表 PDF、横版画面分镜、九宫格、单镜详情、好莱坞式剧本、制作分镜、可编辑 Word 和工程 PDF 或便携包。表格、剪辑工程、字幕各按真实协议能力验收；中文、长文、分页和图片比例实际回读。

无权、已删除或永久删除字段不进新导出；必需技术字段说明用途，内部权限和私人资料不默认夹带。工程 PDF 内嵌堆叠二维码或 DM 分片，用成熟库编码和解码，包含格式版本、包身份、序号总数、分片和整包校验及允许媒体清单，不能包含凭据或授权令牌。

验收从实际 PDF 像素扫码，验证乱序、重复、混包、缺片、容量、未知版本，再走统一预览和导入。没有原图字节只能报告缺媒体，不能冒称已恢复图片。

可见水印可增删改查。不可见水印必须真正隐写并可追溯，二维码、文件校验和元数据不能替代；抗裁剪和截图通过真实样本与无水印对照验证，不预先认定通过。PDF、Word、图片及纯文本分别说明实际实现，不写免责声明标注。

下载和分享重验当前权限、期限、撤销和删除。已下载外部副本不能冒称已擦除。更新时间只来自服务器实际确认，刷新提示区分新数据、本地草稿和冲突，打开页面不制造“刚更新”。



### 13.1 Review → 修改 / 补拍 → Delivery 闭环

Review 永远绑定固定内容或 AssetVersion，不把 Comment 挂在会漂移的“当前 Shot”上。Comment、ReviewDecision 和任务交接各有独立含义；解决一条评论不等于新版本已经制作、QC 或交付。

当 Review 产生可执行修改时，创建或关联唯一 ReworkRequest。ReworkRequest 不能只是 ReviewComment 的字段，因为它需要独立查询、负责人、生命周期、去重、自动化和跨后期/补拍两种去向；它属于 Production scope，通过 typed link 连接源 Review/Comment、受影响 Scene/Shot、输入版本、目标 Task 和后续产物。它不默认成为 Shot 子对象。

后期返工路径为“Review/Comment → ReworkRequest → Task → 固定输入版本 → 新 AssetVersion → Review”。需要补拍时为“Review/现场问题 → ReworkRequest → 拍摄 Task / 待排需求 → SchedulePlan / ShootDay → 现场实际 → Media → 后期 Task → 新 Version → Review”。同一来源、同一目标和同一未解决需求必须幂等，不重复生成任务。

DeliverableItem / Variant 只在存在独立交付对象、查询、权限、生命周期和多版本状态时作为独立 Entity；它们连接所需 AssetVersion、Task、Review/QC 和授权资料。横竖版、时长版、语言版或客户版共享的 Task 只执行一次，差异工作单列。

交付过程不得用一个百分比混合事实。至少分别记录：制作完成、QC 完成、已提交、已送达、接收方已确认、验收通过、退回/替代。退回必须能回到 ReworkRequest / Task；验收通过后仍可有新的追加变体，但不能重写旧验收。

授权资料只管理制作所需的证明及适用范围，不扩展为合同或法务系统。Delivery / Final QC 可以检查相关人物、场地、音乐、素材、字体、Logo/商标、航拍许可等所需文档是否存在、是否在记录范围/期限内；UNKNOWN、缺文件和不适用分开。系统不自动作法律结论。


## 14. 异步任务、事件和自动化

耗时导入、识别、批量导出、语音、缩略图、打包和索引使用持久任务。允许先编辑后上传，但关键事务未确认不能显示完成。

业务与 OutboxEvent 同事务提交，之后发布；版本化事件只带必要身份和固定事实，不复制大正文。重复、乱序和崩溃可重投、去重，队列确认不等于业务完成；消费者改变业务仍走标准命令。

任务固定来源版本、服务配置、权限、删除状态、幂等身份、进度、重试取消、租约和输出引用。取消、撤权、来源改变、永久删除阻断迟到发布；旧执行者不能覆盖新租约，只清自己创建且无引用的暂存文件。

复用成熟队列、存储和服务适配器，不新造队列。自动化使用固定版本规则、有限条件和白名单命令，记录因果、去重并防循环。数据库触发器只保护数据约束，不跨模块自动改排期。

影响记录解释自动更新、冲突、锁定、需要处理、负责人和重试，不是第二份审计。人工智能默认不外发，生成建议经人工或已有明确授权规则接受后走命令；知识核验和接受项目建议是两件事。



### 14.1 全流程自动联动与 ImpactRun

正常制作联动遵循“源事实先提交，未来可推导项自动更新，冲突进入例外”的原则。跨域自动化不能在数据库 Trigger 中直接互改业务表；源命令成功后通过 OutboxEvent 触发受控 consumer，再调用目标 domain 的标准 Command / CAS。

一次源变化形成可解释的 ImpactRun。ImpactRun 记录 source command/event、因果链、已成功目标、失败目标、冲突、锁定项、需人工处理项和重试状态；它不是第二套业务事实，也不复制所有 old/new 正文。

以下变化至少要形成闭环传播：

| 源变化 | 自动重算 / 推进 | 不能自动伪造的事实 |
| --- | --- | --- |
| Scene / Shot 内容或要求变化 | Task applicability、Readiness、人员/场地需求、未锁定排期、后期输入与 Checklist；仅符合 D-35 的自动生成未执行任务可自动停用 | 已开始/有产物 Task 被自动取消、实际出演、资源已具备、已拍摄、Review 已批准 |
| Cast / Person 可用性变化 | 人员时间线、相关 ScheduleItem 冲突、Call Sheet 草稿、受影响负责人 | 自动换演员、旧通告已知悉 |
| Location / 时间窗变化 | 拍摄条目、Company Move、后续地点窗口、通告草稿 | 场地已同意、已到场 |
| ScheduleItem / ShootDay 改期 | Person、转场、需求时段、Call Sheet Draft、需重新确认 Recipient、Media ETA、Post earliest start、Delivery forecast | 自动发布/外发新版通告、已执行事实、旧 Call Sheet revision、固定外部目标已改变 |
| 现场 Actual 延误 | 当天剩余计划、Wrap、转场、后续冲突、后期预计输入 | 自动取消镜头 |
| MediaHandoff / 输入版本变化 | 下游 Task readiness、input stale、Review target；Formal Handoff 仅在完整性与项目配置备份门槛通过后成立，Preview 只允许草稿预处理 | Preview 被冒充正式输入、旧 Task 从未完成过 |
| Review 产生修改 | ReworkRequest、返工 Task 或补拍待排需求 | 评论解决、修改已制作 |
| Delivery 退回 | ReworkRequest、Task、后续 Version / Review | 原验收历史被删除 |
| 经验校准新版本 | 后续新计划的 estimate baseline / workflow suggestion | 已确认计划、历史 Actual 被重写 |

一个目标 consumer 失败不得回滚已经确认的源事实；失败目标保留原因和重试入口。重复、乱序事件通过 idempotency 和 source revision 去重。undo/redo 被视为新的源变化，重新计算未来计划，但不抹掉已发生执行、交接和发布历史。

锁定条目返回 LOCKED，无法满足条件返回 CONFLICT，需要业务选择返回 REQUIRES_USER，可安全推导并实际提交后才是 AUTO_APPLIED。没有真实变化不产生重复任务、通知或 revision。


## 15. 协作、配置与界面扩展

在线状态、光标、选择、聚焦字段和编辑租约临时存 Redis，身份和高亮色由服务器分配并授权广播，不信任客户端自报账号。正文和批注不写 Redis。

协作编辑先取得对象或字段租约；提交时检查租约、权限和修订，失败保留草稿。Redis 故障不能绕过先锁定要求。导入和授权后台规则走自身命令，不伪造在线租约。

模块清单固定声明路由、权限、命令、事件、菜单、视图和交付贡献，不运行用户插件。新页面复用 packages/ui 和公共读写能力，不复制弹窗、提示或巨大导航结构。右键按当前模块、命中对象、选择和权限提供真实动作，行菜单保留向下粘贴，列菜单保留向后粘贴；Ctrl+V 使用对应默认方向，复制与剪切按已接受菜单执行，不恢复独立 duplicate 操作。

配置格式版本与业务修订分开，转换采用集中纯函数；未知新格式拒绝写并保留原记录，不散落界面兼容判断。状态分服务器事实、本地草稿和可重建查询结果，不在多个前端容器保存同一权威值。

首页保留横向整行照片封面、暗色可读覆盖、左侧标题摘要、右侧更新时间人员编辑和打开。用户、组与颜色管理仅按权限展示；不以岗位开放管理员入口。

只在接口接受后补真正缺失的场景、人员、任务、排期、资源需求或知识页面。既有表格、详情、图片预览、设置和其他页面跟随 montblanc08 最新接受版本，不冻结全站，不覆盖其他协作者。

新增页面只验收桌面横屏 1440×900、1920×1080 和正常缩放，检查明暗、键盘焦点、真实读写、失败冲突、刷新及可打断的入场切换退场动画。窄屏和缩放不重新加入本轮门槛。

## 16. 知识库

影视方法、型号参考、时间段需求、项目事实、一次经验、统计和建议分别负责。来源、核验状态和处理方式分开，参数有单位条件和资料版本；人工智能不是独立事实源。

后台用户组保留团队归类，复用已有组成员关系，不建立另一份知识团队成员名单。采集新经验时，贡献范围取当时项目成员所属全部团队的并集并固定；成员之后加入或退出团队，只影响之后的新经验，既有贡献不自动扩散或撤回。没有团队时仅项目内使用。明确撤回、关闭贡献、来源修正或永久删除仍使相关统计失效。

团队只接收符合去标识和样本门槛的汇总，不取得原始回答或项目正文；读汇总仍检查当前团队权限。原始回答按项目和答者权限隔离，不加入个人评分或排名。取消库房不改变知识贡献与原始回答权限。

收工或阶段结束每天跨项目最多三个主题，跳过不阻塞保存或完成；重复事件不重复提问。实测、自报和推测分开，多人回答同一布光不算多个实测样本，未知不填零。

统计保存独立执行单位、项目数、缺失和来源、分位数、方法版本及适用范围；第七十五百分位不是百分之七十五可信度。采用成熟库，按项目和时间留出验证，样本不足明确返回不足，不给伪精确建议。

设备建议引用目标时间范围、需求型号数量和来源版本，说明条件与缺项；不读取或维护已取消的库存、预留和可用数量。知识不能根据型号参考认定此次器材齐备，也不自动换型或改项目需求。

建议固定项目和知识来源版本、条件、缺项及期限，接受后由原业务命令改未来计划。来源撤回、修正和永久删除使建议失效。问题池和排序策略发布后固定版本，先离线回放；知识关系只在真实检索需求出现后建，不将全项目变成万能关系图。



### 16.1 项目 Actual → QA → 估时与流程校准闭环

经验库的主要用途是校准后续项目的预计时长和流程关联，不建设“常用设置、设备使用经验、常见问题百科”。具体摄影机、焦段、曝光、灯位、AE/UE 参数和设备组合始终属于 Project / Scene / Shot / Task 的实际数据。

可进入校准的 Actual 至少来自 Task 实际用时、ScheduleItem 的 Prep/Setup/Shoot/Reset/Move/Wrap 实际区间、MediaHandoff、返工/补拍和阶段完成事实。QA 只补充原因、上下文和人工解释，不替代实测 Actual。

经验闭环为：

```text
Project Actual
→ ExperienceObservation / QA
→ 去重与质量核验
→ Aggregate / EstimateProfile
→ Calibration Candidate
→ K3 受权 Recommendation / 原业务 Command 接受
→ 人工确认或已批准规则
→ 更新项目模板 / Shot Pattern / Task estimate / Dependency / Checklist 基线
→ 仅影响之后的新计划或明确重新预测
```

一次项目偏差不能直接修改全局基线。校准必须记录样本数、独立执行单位、适用项目/Scene/Shot/Production Method 条件、版本和来源；不足时返回 INSufficient data。新 EstimateProfile 不重写已确认计划、Actual、旧通告或旧任务。

流程关联校准可以提出“某 Shot Pattern 通常还需要 Tracking Task”“某类 Scene 需要额外共享准备”等候选，但正式改变 WorkflowTemplate / Dependency / Checklist 仍走其 own revision 和审核命令，保留旧模板实例所用版本。


## 17. 删除、迁移和恢复

普通删除保留历史，同身份恢复；永久删除预览影响并确认后清受控正文，不能由临时留存定时任务代替。没有归档操作。

永久删除处理当前值、快照、独立历史正文、所有用户撤销、导入计划来源、配置引用、审阅、画板素材引用、任务输出、索引缓存和受控下载；共享原图按引用保护。先使正文不可读并记无正文删除标记，物理清理可重试并报告进度。

正式来源和产物不套临时期限。备份恢复先补删除记录，旧版本、旧任务和旧导入不能复活永久删除正文。项目删除处理本项目需求与来源引用；不存在库存、预留或库房删除流程。

迁移先核对唯一实际 Alembic 最新节点，由集成者独占结构链；不改已发布迁移，不编造父提交。场景多关系转换保留镜头身份，旧单场景只转主关系，兼容写不能丢其他关系。

数据库接受必须用真实 PostgreSQL 空库和上次接受结构的合成副本，验证外键、唯一、格式约束、并发锁序、回滚、备份恢复和删除记录。SQLite 单测不替代。已经接收新写入后前向修复，不降级删表丢数据。

旧数据库不回填，本轮不操作生产、服务器或已有预览。真实媒体、凭据、私有地址和未脱敏截图不入 Git；原截图固定本地保留，公开证据用合成或脱敏副本。

## 18. 工作包、依赖与可复用验收

每包独立负责人、依赖、可改与禁止文件、实际基础提交、接口迁移、门槛、回退和证据。机器清单的进度不是产品迁移完成状态；文件存在或结构校验通过不能登记为已接受。

| 阶段 | 工作内容 |
| --- | --- |
| B0 | 核对画板、导入、导出现有代码及未完成验收，不重做界面 |
| E0、E1 | 幂等回执、唯一历史、配置转换、人员身份和项目权限 |
| E2、E3 | 组织、场景、选角、资源需求、来源识别、实体字段和共享视图 |
| E4、E5 | 任务依赖、固定产物、事务事件、持久作业及存储 |
| E6 | 时间段需求、共用计算、排期和通告 |
| E7、E8 | 导入导出、来源追踪、工程码、自动联动和例外处理 |
| E9 | 已接受接口上的独立缺失页面，既有页面由指定负责人接入 |
| K0至K5 | 知识参考、经验、统计、资源约束建议和真正缺失知识页面 |

路由总入口、模型导出、迁移链、历史快照注册和协作台账由集成者串行处理。各包只改分配文件，完工先拉取别人增量，不能用旧整份文件覆盖。后端变化、缺失页面、允许范围和验收责任同步写衔接账本。

验收覆盖一百二十镜头多制作方式项目、多场景剧情、多人共享视图、跨项目资源、普通及永久删除、二次导入、横竖交付回读、图片画板与语音、制作联动和知识闭环。资源重点验证来源识别、缺数量或型号、分时、明确共用、未排期、授权及不产生库存结论。

具体样例沿 FX-01 至 FX-25、KL-01 至 KL-11 执行，不另造平行验收制度。真实页面和文件证据不能被后端通过或构建成功替代。

每次接受记录实际基础提交、改动摘要、执行时间与命令、断言、退出码、脱敏证据和未通过项。完成一包就更新文档、显式暂存、检查、提交推送及核对远端；不混入别人草稿，不冒称持续集成、数据库或视觉通过。

“可执行方案”要求分支、职责、约束、依赖和门槛明确；“功能完成”还要求真实注册、使用入口和实际验证。本轮完成的是需求审计修订，尚未实现的新模块继续保留未开始状态。


## 19. 全流程功能闭环总合同

FrameForge 的功能完成不能用“页面存在”“模型存在”“接口可调用”判断。一个环节只有在上游事实能够驱动它、用户可以完成本环节、结果能成为下游明确输入、失败/冲突可解释、历史可追溯并且可以回流时才算闭环。

### 19.1 主制作链

Canonical 功能链为：

```text
Project / Template
→ Script / Scene / Shot
→ Requirement / Production Method
→ Task / Dependency / Handoff
→ Person / Cast / Location / 时间段资源需求
→ SchedulePlan / ShootDay / ScheduleItem
→ Company Move / Daily Plan
→ CallSheetRevision / Personal Call
→ On-set Actual
→ Media / Integrity / Backup / Handoff
→ Post Task (Edit / AE / UE-3D / Sound / Color)
→ AssetVersion
→ Review
→ Rework or Reshoot
→ Deliverable / QC / Delivery
→ Actual / ExperienceObservation
→ Estimate / Workflow Calibration
→ 下一项目或下一次重排
```

这条链允许并行和回退，不强制线性瀑布：边拍边剪、部分 Scene 先交接、UE/AE 与实拍并行、Review 触发补拍都合法。任何视图、看板或导出只是这组事实的 projection，不建立第二套状态 owner。

### 19.2 每一环的完成条件

| 环节 | 入口事实 | 本环必须产出 | 下游闭环条件 |
| --- | --- | --- | --- |
| 项目/模板 | Production + 项目类型 | 实际启用阶段、角色/任务模板、Checklist | 能生成/创建 Scene/Shot 和真实 Task，不只是展示模板 |
| Scene/Shot | 创作内容、多 Scene relation | Requirement、Production Method、明确 override | 能决定 Task applicability、人员/地点/需求和 Readiness |
| Task | 模板或人工工作需求 | 主责/协作、输入、计划、产物、依赖、实际状态及适用性来源 | 失效的自动任务按 D-35 停用；已执行事实保留；下游依赖只能由仍适用且满足固定输入/交接的事实解锁 |
| 人员/选角 | Person、Character、CastAssignment、Membership | 明确出演/任职与 Availability | 排期能使用同一 Person 检冲突并生成个人时间线 |
| 排期 | Task/Scene/Shot、人员/场地、时间段需求 | SchedulePlan、ShootDay、ScheduleItem、锁定/冲突 | 能生成转场、通告和后期预计输入 |
| 转场 | 前后 ScheduleItem、Location | 可解释 Move 区间及组成时长 | 下一拍摄条目 earliest start 正确受影响 |
| 通告 | CURRENT Plan + 当日事实 | 自动更新的 Draft、差异/需重确认列表；经授权显式发布后才产生 immutable CallSheetRevision + Recipient/ack facts | 自动化不发布或外发；发布后可确认、显式改版并保留旧 revision |
| 现场 | ScheduleItem + Readiness | Actual、镜头满足/补拍事实、素材来源 | Media 可以追溯拍摄来源并进入检查/交接 |
| 素材 | MediaAsset / AssetVersion | integrity、项目配置的 backup verification、Preview 与 Formal Handoff 分离 | 草稿预处理可消费 Preview；正式 Post readiness / Review / Delivery 只有固定版本 Formal Handoff 后成立 |
| 后期 | Post Task + 固定输入 | 新 AssetVersion / 产物 | Review target 固定版本 |
| Review | 固定版本 + Comment/Decision | 已解决或 ReworkRequest | 修改进入 Task，补拍进入待排，不停在评论 |
| 补拍/返工 | ReworkRequest | Task 或 Schedule demand + 新产物 | 回到 Media/Post/Review，源问题不重复建单 |
| 交付 | DeliverableItem/Variant + QC + 授权资料 | submit/deliver/ack/accept/reject 等独立事实 | Reject 回返工；Accept 固定当时版本 |
| 经验校准 | Planned vs Actual + QA | Aggregate / EstimateProfile / calibration candidate | 只在确认后更新未来 estimate/workflow/checklist 基线 |

### 19.3 闭环所需 Entity 准入说明

以下对象如果进入实现，必须继续遵守 §3.1；这里补齐为什么不能只是某个现有 Entity 的字段：

| Entity | 为什么不能只做字段 | 独立查询/权限/生命周期 | History / Automation | 主要 typed relations |
| --- | --- | --- | --- | --- |
| Task | 一个工作可关联 Scene、多个 Shot、Asset、人员和交付，且有独立执行/交接 | 是；独立负责人、revision、状态与权限 | 执行/交接独立历史；参与 DAG 与自动化 | Scene、Shot、Person、AssetVersion、ProductionStep、Deliverable |
| SchedulePlan | 需要多个方案和唯一 CURRENT，不能把“计划日期”塞回 Shot | 是；DRAFT/CURRENT/SUPERSEDED | 独立计划历史；驱动冲突/通告/预测 | ShootDay、Unit、Task、Scene/Shot |
| ScheduleItem | 同一 Shot 可跨日/补拍/多 Unit，每次安排有独立时段与 Actual | 是；计划/实际、锁定与冲突 | 计划更正/Actual 独立；驱动后续联动 | Scene、Shot、Task、Person、Location、需求 |
| CallSheetRevision | 已发布内容必须固定且可被确认，不能随 CURRENT 排期漂移 | 是；发布/撤回/接收人权限 | 独立发布历史；重要变化触发重确认 | ShootDay、ScheduleItem、Person、Location |
| ReworkRequest | Review 问题需要跨后期和补拍、去重、负责人和状态 | 是；独立 open/resolved/superseded 语义 | 触发 Task / Schedule；保留源问题 | Review/Comment、Shot、AssetVersion、Task、Deliverable |
| DeliverableItem / Variant | 一个项目有多个真实交付对象、不同规格和验收事实 | 是；接收范围、QC/提交/验收生命周期 | 退回触发返工；发布事实独立 | AssetVersion、Task、Review、Authorization |
| ExperienceObservation | 项目事实不能被 QA/解释覆盖，经验需独立质量/撤回 | 是；原始项目权限与团队汇总权限分开 | 不进创作版本；进入校准作业 | Task、ScheduleItem、Scene/Shot、KnowledgeSpace |
| EstimateProfile | 统计版本必须冻结样本/算法/适用范围，不能覆盖模板字段 | 是；不可变计算版本 | 新版本只影响未来建议/预测 | ExperienceObservation、Pattern、WorkflowTemplate |

MediaHandoff 只有在“一份素材存在多消费者、独立确认、更正/撤回或单独权限”时才升为独立 Entity；否则先以 TaskAssetVersion + 接收/检查事实表达。Company Move 当前是 ScheduleItem 类型，因为它没有脱离排期方案的独立 owner、权限和生命周期，不新增一级对象。Take 继续遵循 D-15，不为了补图预建空 Entity。

### 19.4 端到端自动化验收场景

使用合成项目验收，不依赖经济系统：

- 两个 Scene、六个 Shot，其中一个 Shot 关联两个 Scene；
- 两名演员/现实人员、摄影/灯光/制片/剪辑等任职；
- 两个 ShootDay、两个 Location、至少一次 Company Move；
- 一项共享 Scene 准备 Task 和多项 Shot 专属 Task；
- 一组明确时间段器材/道具需求；
- 一条拍摄后 Edit → AE 或 UE/3D → Review → Delivery 链；
- 一个固定 Delivery target 和一项授权资料检查；
- 一个 Review 修改走后期返工，一个问题走补拍；
- 项目结束产生 Planned vs Actual 并进入经验校准候选。

验收操作至少包含：

1. 将一个 Scene 从周三移到周五；未锁定的人员安排、转场、需求时段、通告草稿、媒体预计交接、后期 earliest start 和交付预测自动刷新；因 Scene / Production Method 变化而失效的自动 Task 按 D-35 分流：未开始无产物的自动停用，已开始/已交接/有产物的保留并提示负责人。
2. 其中一名演员周五不可用、下一场地点窗口不足、一个后期目标日期固定；三项必须形成可解释例外，而不是静默改数据。
3. 排期变化先自动刷新 Call Sheet Draft 并标出需重新确认的人；系统不得自动发布或外发。由有权限的人显式发布新 CallSheetRevision，旧 revision、旧确认和旧计划基准仍可追溯，重要变化需要重新确认。
4. 第一场实际超时，系统重算 Company Move 和当天剩余计划；锁定条目不移动，预计 Wrap 和冲突更新。
5. 拍摄完成后建立素材来源，分别记录完整性、项目配置的备份验证、Preview 与 Formal Handoff；备份未满足时允许草稿预处理，但正式后期输入不得伪 Ready。
6. Review 评论生成唯一 ReworkRequest；后期修改产出新 AssetVersion，补拍问题重新进入排期并产生新媒体，再回到 Review。
7. Delivery 被退回时回到 ReworkRequest / Task；再次提交和最终验收不覆盖第一次退回历史。
8. 收工/阶段结束生成经验观察；校准候选可以更新之后的预计时长或流程关系，但不能自动改当前项目已确认计划或具体摄影/AE/UE 设置。
9. 任一 consumer 中途失败后，源命令仍成立，ImpactRun 显示失败目标并可重试；重复 event 不产生重复 Task、通告或返工需求。
10. 全流程任何一步的权限撤销、revision 冲突、永久删除或锁定条件都必须返回明确结果，不能通过前端本地状态假装成功。

通过上述场景才可以宣称“制作功能闭环”。单独通过 Shot 编辑、Task API、Schedule 页面、Review 页面或 Export 构建都不能替代端到端闭环验收。



### 19.5 闭环环节、工作包与验收门槛映射

总纲中的闭环环节必须有机器工作包 owner 和至少一个可执行 gate；没有对应包的文字要求不能被视为已纳入实施。现有通用基础门槛继续复用，下表增加本轮闭环专属门槛。

| 功能环节 | 主要工作包 | 专属/关键 Gate | 验收重点 |
| --- | --- | --- | --- |
| Scene/Shot → Task / DAG / Handoff | E4-TASK | FX-08、FX-09、FX-26 | 模板/制作方式真实生成任务；来源失效按 D-35 自动停用边界；已执行事实不被删除 |
| Person/Cast/Location → 排期 | E2-CAST、E2-SHARED-RESOURCE、E6-SCHEDULE | FX-13、FX-19、FX-20 | UNKNOWN 不当可用；一人多岗不重复；锁定和冲突可解释 |
| Schedule → Company Move → Call Sheet | E6-SCHEDULE | FX-13、FX-27 | Move 影响 earliest start；排期变化只改 Draft；发布/发送必须显式 |
| On-set Actual → Media 正式交接 | E6-MEDIA-HANDOFF | FX-28 | Actual 可追溯；完整性+项目配置备份门槛；Preview 与 Formal Handoff 分离 |
| Media → Post Task → Version | E4-TASK、E6-MEDIA-HANDOFF | FX-09、FX-28 | 固定 AssetVersion 输入；Preview 不冒充正式 Ready；输入变化只使相关分支过期 |
| Review → Rework / Reshoot → 再 Review | E7-DELIVERY-LOOP | FX-29 | ReworkRequest 去重；返工回 Task，补拍回 Schedule，产生新版本再审 |
| Deliverable / QC / Delivery | E7-DELIVERY-LOOP、E7-EXPORT | FX-15、FX-29 | QC、提交、送达、确认、验收、退回分开；退回能回返工 |
| 全流程 Impact | E8-IMPACT | FX-10、FX-17 | 源事实先提交；未来项自动联动；LOCKED/CONFLICT/REQUIRES_USER 可解释可重试 |
| Actual → QA → Calibration → 未来基线 | K1-EXPERIENCE、K2-CALIBRATION、K3-RECOMMENDATION | KL-04、KL-05、KL-06、KL-07、KL-08 | 实测与解释分开；去重；不可变 profile；必须经受权接受后才更新未来估时/流程候选 |

FX-26 至 FX-30 的具体 fixture 写在实施计划并列入机器清单。任何上游工作包即使单独 accepted，只表示该环节能力通过，不代表 Z0 或整个 Production workflow 已闭环。
