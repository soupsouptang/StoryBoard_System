## Infrastructure ownership note (2026-10-02)

The infrastructure remediation did not add or claim Legacy API route parity. `apps/api` remains the VNext HTTP/authentication owner; production configuration requires explicit secrets and database URLs, and Alembic owns schema changes. The Web production client defaults to same-origin API routing, with Nginx routing `/api` and WebSocket upgrades. CI validates API contracts and a clean PostgreSQL-to-Alembic-head rehearsal; a passing migration job is not evidence of data backfill or production cutover. Authentication implementation details and current CI status are recorded in [ACTIVE_WORKSTREAMS.md](ACTIVE_WORKSTREAMS.md) and [CANONICAL_OWNER_MATRIX.md](CANONICAL_OWNER_MATRIX.md).

## Shared contract boundary

- L: session cookie and CSRF on mutations (`server.py:1740-1754`); SQLite `storyboard.db` under `STORYBOARD_DATA_ROOT`, with command modules and project bundles. Anonymous health and share routes are exceptions. L remains the configured runtime.
- V: bearer JWT on business routes via `apps/api/app/api/v1/deps.py`; `AsyncSession` and SQLAlchemy models use `DATABASE_URL` (`apps/api/app/core/database.py`). Anonymous health and share GET are exceptions. V routes exist but are **IMPLEMENTED_NOT_INTEGRATED** until actual clients and deployment switch.
- F: Legacy session cookie or bearer token via `fastapi_app/dependencies.py`, direct SQLite connection and `SQLiteUnitOfWork`; presence routes do not depend on that authentication. `fastapi_app/main.py:57-62` mounts F, but the inspected startup paths do not start it; `storyboard-system/tests/test_fastapi_app.py` directly constructs its app. Classify F as **test-only parallel implementation**, not the running owner.

Every V path in the table is the **CANONICAL target**, not a cut-over runtime route. `DUP` = parallel route; `DIFF` = similar purpose, different method, shape, auth, mutation, or storage; `MISS` = no V route in `apps/api/app/api/v1`; `V-ONLY` = V route without a matching L route. ## Current VNext gates

1. **VNext API contract first:** implement and test only the routes the current VNext product needs. Legacy endpoint names, cookies, CSRF/session behavior and payload shapes are not compatibility requirements.
2. **No Legacy database/API cutover:** do not rehearse SQLite→PostgreSQL backfill, route-by-route switching, dual writes or old-client compatibility. PostgreSQL acceptance is clean database → Alembic head plus VNext integration/transaction tests.
3. **Portable project bridge is the sole exception:** Legacy must be able to export a self-contained project artifact; VNext must validate, preview and map/import that artifact. It is explicitly allowed to modify Legacy exporter code/schema to make this contract reliable. The endpoint that produces the file does not need to be reproduced in VNext.
4. **Retire Legacy runtime after extraction:** transfer any still-required product semantics into VNext and preserve representative export fixtures. Old route trees may then be removed without proving route parity or zero old-client consumers.

No route in this inventory becomes a compatibility gate merely because a Legacy equivalent exists.
