### 1.4 知识库维护

岗位定义由系统最高管理员及后台通过统一系统权限/用户组授权的知识维护动作管理，不另设知识库专用管理角色。个人与团队均从库中选择，不自行创建新岗位定义；专业知识、维护动作和来源核验遵循[知识库基础合同](KNOWLEDGE_FOUNDATION_AND_EXTENSIBILITY_2026-10-05.md)。

团队管理员可以维护团队所需岗位的选择，作为招聘和组队参考；这不属于修改知识库岗位名称、分类或职责。

## 2. 必须分别记录的对象

| 对象 | 含义 |
| --- | --- |
| 个人账号 | 用户登录及个人身份 |
| 个人能力档案 | 用户自行声明掌握的技能，可从知识库多选 |
| 团队展示能力 | 用户提供给某一个团队、按规则生效的能力集合 |
| 团队岗位需求 | 管理员选择的需求，类似招聘信息，用于能力覆盖建议 |
| 成员关系 | 用户是否正式加入某团队、是否申请退出或已离队 |
| 管理身份 | 团队管理员或Agency管理员的管理范围 |
| 项目成员与分工 | 用户在某项目实际负责的工作及相应编辑范围 |
| 历史摘要 | 用户参加过哪些团队、项目及工作的个人历史记录 |

技能、任职与管理权限分别管理。拥有导演、制片等技能，不自动获得管理权。成员加入团队，不自动获得全部团队项目内容访问权。

## 3. 个人注册与能力档案

1. 注册先成为个人用户，并先完成职能能力设定，类似求职资料；只能从知识库选择。
2. 无论是否加入团队，个人资料中的技能增删均由用户自行操作，无需任何团队批准。
3. 新增个人技能只更新个人能力档案；是否向某个团队展示，由用户另行选择和申请。
4. 删除个人技能直接更新所有已加入团队的展示集合，并通知各团队管理员，无需审批。
5. 当前个人档案及团队展示呈现最新有效结果；审批中的新增展示不能冒充已经批准。
6. 未确定技能认证、考核或熟练度制度，个人声明不自动成为专业认证。

## 4. 向团队展示能力

| 操作 | 审批与结果 |
| --- | --- |
| 首次入队选择展示技能 | 用户从个人能力选择提交，管理员批准后可用于项目工作分配 |
| 新增向某团队展示的技能 | 用户申请，该团队管理员批准后生效 |
| 审批等待或拒绝 | 原有效展示内容保持不变 |
| 仅停止向某团队展示技能 | 用户直接操作，无需审批，自动通知该团队管理员 |
| 从个人档案删除技能 | 同步从所有已加入团队移除展示，通知各管理员 |
| 管理员修改用户展示能力 | 无权自行增删，只能审批用户的新增展示申请 |

邀请接受或有效串号决定入队，首次技能审批不作为第二次入队审批。各团队展示独立，甲团队批准某能力不自动令乙团队批准。

普通成员只查看对方在本团队展示的技能。管理员可以查看成员拥有但未在本团队展示的其他能力；看见这些能力不表示可以直接使用其分配工作。

示例：个人具备摄影、剪辑和AE能力，向甲展示摄影、剪辑，向乙展示剪辑、AE。甲乙分别审批和显示；用户在甲停止展示剪辑，不影响乙；用户从个人档案删除剪辑，则甲乙均同步移除。

## 5. 团队创建与成员加入

### 5.1 团队创建

个人用户创建独立团队，自动成为该团队唯一管理员。界面不体现团队所有权，管理员实际掌握团队最高管理权。

### 5.2 加入方式

- 邀请：被邀请用户接受后加入。
- 唯一串号：输入当前有效串号即自动加入，不另设管理员入队审批。
- 管理员可随时更换串号，生成新串号时旧串号立即作废；已有成员不受影响。
- 任一加入方式均受200人上限及Agency触发条件约束，正确串号不绕过这些规则。

### 5.3 人数

每个团队硬性上限200人，含独立团队及Agency所属团队。

人数按正式成员身份去重，包含作为正式成员的管理员；待加入、已离队不计，退出尚未获批仍计。同一用户拥有多少技能、承担多少岗位，都只占该团队一个成员名额。

另设预期人数，表达管理员预计组织多少人，供能力分析使用，不是成员上限。原“知识库岗位数×2”、278人推算及单岗位2人限制均取消。岗位库数量、管理员需求选择和工作分配不改变200人上限。

## 6. 团队岗位需求与能力建议

管理员维护的需求类似招聘信息，用户个人能力类似应聘资料，两者无必须一一对应关系。

管理员从已有知识岗位选择团队需求，用于项目建立时判断能力是否完整。团队需求可供团队项目复用，不产生知识库新定义，不直接授予技能、实际工作或权限。

系统可结合创作链条、项目制作方式、预期人数及成员能力，提示能力覆盖、缺失岗位、人数或兼任问题。建议不强制补齐，也不强制生成任务。团队可由全部剪辑人员组成，单岗位任职人数不受2人限制。

提示应分别表达团队目前没有某项有效能力，以及本项目有能力但尚未安排负责人。纯MG项目不按实拍摄影链条强制提示摄影缺口。具体建议算法及默认需求模板仍待设计，不能把推演建议写成已实现结果。

## 7. 团队管理权与移交

每个团队一名管理员，无额外管理员或部分管理授权。

独立团队管理权可移交给任意现有团队成员，也可以转回最初创建者。成功后新管理员接手全部团队管理权，原管理员成为普通成员；双方既有项目职责不随管理身份变更。

团队计入当前管理员的管理团队数量，不按创建历史计数。A移交甲给C后，甲计入C、不再计入A；这不自动解除A的成员身份。

C已管理两个独立团队时，按独立团队移交规则本次转移失败。接收第二个团队也检查“两团队各至少5人且共同成员≤3人”的Agency条件；C拒绝成立Agency，转移失败，原管理权保持。

团队管理员本人退出，先移交管理权再办理退出。Agency内团队的管理员指派、改派由Agency管理员执行，按Agency层的权限规则管理。

## 8. 项目创建、组队与归属

### 8.1 创建与组队顺序

可先组队再创建项目，也可先创建项目再组队，无固定先后顺序。

组队前任何个人用户均可创建个人项目，归自己管理。团队场景中的项目由具有对应管理权限的管理员创建；加入团队不剥夺用户独立创建个人项目的能力。

### 8.2 个人项目进入团队

先前创建的个人项目可以分享至团队；分享后直接成为团队项目，按团队及Agency管理规则管理。本次决定不增加一套永久并列的个人项目管理权，也不要求额外执行一次管理权转交。

个人项目转入团队须由目标团队管理员确认接收。项目具有唯一归属，不同时属于多个团队或Agency；分享不是复制第二份项目或增加平行归属。未确认项目能否日后在两个团队之间整体转移，不能据唯一归属自动推断允许或禁止这种变更。

### 8.3 分工

管理员从现有团队成员中组队，依据其在本团队最新、有效展示的技能选择本次工作。一人多岗、一岗多人均允许，实际任务主责/协作沿任务合同处理。

管理员可直接分配及调整项目工作，包括已有项目新增分工，无需成员逐次重新申报，操作后通知用户。不能依据尚未批准、未向本团队展示的能力分派或交接。

成员可以主动申请增加或减少实际负责工作，管理员批准后生效；等待或拒绝时原分工保持。

### 8.4 技能变化与已有项目

个人能力增删和团队展示变化不自动更改已完成或正在进行项目的原分工。新建项目及已有项目新增分工使用最新有效展示能力。新规则不以重算当前技能改写历史责任或执行事实。

## 9. 查看、编辑与隐私

| 身份/入口 | 权限 |
| --- | --- |
| 个人项目创建者 | 管理尚未成为团队项目的个人项目 |
| 普通团队成员默认项目列表 | 显示自己负责、参与的项目 |
| 普通成员查看全部 | 列出本团队全部项目，未参与项目标记且不可进入内容 |
| 项目成员 | 可查看完整项目，仅编辑分配给自己的工作 |
| 团队管理员 | 进入并管理本团队全部项目 |
| Agency管理员 | 管理所属所有团队及团队内部项目，可指派、改派团队管理员 |
| 离队用户 | 保留个人历史摘要；项目内容访问另行授权 |

管理权、岗位分工、项目参与关系和技能展示各自独立。退出或管理权移交后按新的有效身份检查访问；保留历史摘要不自动保留原项目权限。

跨团队关系只由本人查看和管理；普通团队成员不因同团队身份看到对方在其他团队的关系或项目内容。Agency管理员对所属团队的组织管理权限适用本节，不因此查看所属范围之外的其他团队。

个人页面展示本人加入的Agency及相关团队、其他用户管理的独立团队、自己管理的独立团队/Agency、各团队负责项目、历史团队和历史项目。组织关系可见不等于获得每个项目内容权限。

具体权限独立记录于[权限规则文档](PERMISSION_RULES_2026-10-05.md)。本节保留已确认的概要；“只编辑自己的工作”映射到镜头、字段、共享内容及配置的细则仍待该权限文档确认。

## 10. 退出、移除与交接

用户主动退出不需要管理员批准，被移除需管理员操作。

处理时将未完成职责交给现有成员，依据其在本团队有效展示的技能；不能使用未展示能力。若无人能接手或胜任，仍允许批准后正式离队，剩余工作持续标红提醒管理员和团队成员，不阻断业务流转。

缺人提醒不伪造接收人、技能或完成记录。成员离队不清除其历史责任和执行事实。团队管理员本人按第7节先完成管理权移交。

所有离队成员保留个人历史摘要。历史项目内容默认不随摘要继续开放，需要另行授权。

## 11. Agency成立条件与团队归属

### 11.1 条件

| 情况 | 规则 |
| --- | --- |
| 单个独立团队达到10人 | 提示下一位加入前需成立Agency |
| 准备加入第11位成员 | 先成立Agency，完成后才可继续加入 |
| 同一当前管理账号的两个独立团队各≥5人，共同成员≤3人 | 独立触发条件，在导致条件成立的操作前提示并要求成立Agency |
| 准备新建第三个独立团队 | 无论重合多少，均须先成立Agency |

以当前管理权归属判断，不把仅加入的团队、最初创建但已移交的团队或成员自己管理的团队算到该账号名下。共同成员按两队正式成员身份交集计算。原60%重复率方案取消。

这些是独立团队转为Agency组织方式的条件，200人是每团队容量限制，二者分别检查。个人参与多个已有团队不要求其因此成立Agency。

### 11.2 成立与管理

Agency成立时，创建账号当前拥有管理权的全部团队纳入；该账号仅加入而未拥有管理权的团队不纳入，其他成员管理的团队也不自动纳入。

Agency有一名固定最高管理员，管理所属全部团队和团队内部事务。Agency不可移交给任何成员。每个团队可指定一名团队内成员为管理员，只管理本团队内部；Agency管理员可指派、改派。

成立Agency后，Agency所属团队的建立及解散功能由Agency管理员掌握。团队管理员不能自行解散所属团队或将其脱离Agency；成员退出某团队不等于该团队脱离Agency。团队规模允许超过10人和15人，仍受每队200人限制。

## 12. Agency及团队解散、归档

Agency最高管理员可自行删除、解散Agency，不需成员同意，须通知成员。

- 若Agency管理员同时担任某所属团队管理员，该团队一并删除、解散。
- 由其他用户担任管理员的团队，保留与否由各团队管理员决定。
- 保留后触发Agency条件，该管理员需成立Agency，或调整人数/移交部分团队，使其满足独立团队条件；不能直接忽略条件。

团队解散后，项目及历史记录归档，停止团队协作，项目内容保留；后续访问、导出由原管理账号按归档规则处理。所有成员均保留个人历史摘要，摘要不自动授予归档项目内容访问权。

“删除/解散组织”不等于永久删除项目及媒体。Agency存续时单个团队不得自行脱离；Agency整体解散后，其他团队管理员决定保留的规则仍沿上述已确认流程。保留决策过程中的临时状态和处理时点属于后续设计。

| 个人能力增删 | 用户自行操作 | 删除时通知各相关团队管理员 |
| 停止某团队技能展示 | 用户自行操作 | 通知该团队管理员 |
| 管理员分配或新增项目工作 | 管理员直接操作 | 通知受影响用户 |
| 成员申请增减工作责任 | 管理员审批 | 结果呈现待界面设计 |
| 退出/移除 | 管理员审批并处理交接 | 无人接手时持续标红提醒管理员及团队成员 |
| Agency解散 | Agency固定管理员决定 | 通知成员 |

业务通知的渠道、已读方式、频率及文案尚未确定；不自行添加邮件、短信或站外发送。本文没有向任何人实际发送通知。
