## 1. 权限设计总原则

1. 权限以“组织身份 + Project Admin + 项目岗位职责 + 职责治理能力 + 已审批的跨职责授权 + 项目自定义权限模板”组合计算。
2. Project Creator 不再作为独立角色；创建项目的用户直接成为 Project Admin。
3. 不设 Personnel Admin，不设 Creative Admin。
4. Team Admin、Agency Admin、System Admin 的管理身份不自动转换成项目专业内容编辑权；需要编辑某项专业内容时，必须在项目中具有对应岗位职责。
5. 内部 Project Member 默认可以查看完整项目内部生产内容，并默认可以创建、编辑自己岗位职责范围内的内容。
6. 内部 Project Member 不按 Shot、Task、排班或拍摄日期切割职责权限；职责范围在整个项目内生效。
7. 同一职责内的数据不属于某个填写者个人。拥有该职责的项目成员可以修改同职责其他成员创建或修改的内容，系统保留版本与修改记录。
8. 职责外内容默认可查看、不可编辑；需要编辑时走跨职责审批。
9. 编辑权与审批权严格分离。
10. 多岗位、多职责权限只做**权限集合相加（并集）**，不做“取最高等级”，不把某个职责的 Lead 权限扩散到另一个职责，也不生成任何原本不存在的权限。
11. 一个对象同时属于多个职责时，每个动作都必须保留其权限来源职责；最终有效动作集合等于用户在这些职责上已经拥有的动作集合之并集。
12. Work / Episode 仅组织项目，不产生权限。
13. 拍摄计划负责计划与通告，不作为权限判定来源。
14. 本文件不新增任务驱动权限模型。

## 3. Project Admin

### 3.1 身份

- Project Creator 与 Project Admin 合并，不再保留独立 Project Creator 角色。
- 项目创建者创建项目后直接成为 Project Admin。
- Team Admin 可按已确认的项目治理规则明确指定 Project Admin。

### 3.2 Project Admin 可以管理

- 项目成员；
- 项目岗位；
- Project Admin 相关项目治理；
- 项目设置；
- 项目权限模板；
- 没有目标职责 Lead 时的跨职责编辑审批；
- Lead 扩大分享范围的审批；
- 项目级治理与高风险操作。

### 3.3 Project Admin 不自动获得

Project Admin 身份本身不自动获得任何导演、摄影、灯光、美术、录音、动画、三维、剪辑、声音、交付等专业职责编辑权。需要编辑对应职责内容时，用户必须同时拥有对应项目岗位。

## 4. 内部 Project Member 默认权限

内部 Project Member 默认可以查看完整项目内部生产内容。

在本人一个或多个项目岗位的职责范围内，默认拥有：

| 动作 | Responsibility Member | Responsibility Lead |
| --- | ---: | ---: |
| 查看职责内容 | ✓ | ✓ |
| 创建职责内内容 | ✓ | ✓ |
| 编辑职责内内容 | ✓ | ✓ |
| 修改同职责其他成员创建的内容 | ✓ | ✓ |
| 删除职责内内容到回收站 | ✓ | ✓ |
| 恢复职责内内容 | ✓ | ✓ |
| 导出职责内内容 | ✓ | ✓ |
| 内部分享 | ✓ | ✓ |
| 永久删除职责内内容 | — | ✓ |
| 对外分享职责内内容 | — | ✓ |
| 审批进入本职责的跨职责编辑 | — | ✓ |
| 本职责审批动作 | — | ✓ |

“—”表示本身份本身不授予该动作，不代表可由其他已确认身份或经审批授权取得。

## 5. 多岗位与多职责：权限只相加，不升级

同一用户可以在一个项目中同时拥有多个岗位，职责权限相加。

例如：

- Camera 职责已授予：查看、创建、编辑、删除到回收站、恢复、导出、内部分享；
- Lighting 职责已授予：上述基础动作 + 永久删除 + 职责内对外分享。

当某个对象同时属于 Camera + Lighting 时：

```text
effective_permissions
=
camera_permissions
∪ lighting_permissions
```

结果只包含两个职责已经存在的动作集合。

**禁止以下计算：**

```text
Lighting = Lead
→ 整个对象按 Lead
→ Camera 自动获得 Lead 权限
```

也禁止由“最高等级”“最大权限”“对象级提升”等方式产生未被任何职责实际授予的权限。

每个动作都必须能追溯到权限来源职责。

## 6. 职责范围与项目范围

### 6.1 不逐 Shot 分配

专业负责人和普通职责成员均不需要逐个 Shot 分配权限。

只要某用户在项目中拥有某岗位职责，该职责对整个项目中属于该职责的内容生效。

### 6.2 不按排班裁剪

不需要排班权限。

成员不会因为某一天未参与拍摄而隐藏项目内容或失去职责编辑权。拍摄计划、拍摄日期、Call Sheet 只表达制作安排，不产生或撤销专业职责权限。

### 6.3 职责内允许创建

普通职责成员可以创建属于本人职责范围内的新内容，不要求先由 Lead 或 Project Admin 创建。

### 6.4 同职责协作

同职责内容属于职责协作范围，不属于单个作者。

因此同一职责的成员可以直接修改彼此创建的职责内容；修改历史、版本与操作人必须保留。

---

## 7. 跨职责编辑

内部 Project Member 可以查看职责外内部项目内容，但不能默认修改。

需要修改职责外内容时：

1. 用户发起跨职责编辑申请；
2. 目标职责存在 Lead 时，由目标职责的 Lead 审批；
3. 目标职责没有 Lead 时，由 Project Admin 审批；
4. 只有审批明确授予的职责/内容/动作生效；
5. 不因为一次审批自动扩大到其他职责或其他未授权动作。

编辑权与审批权严格分离。

---

## 8. 删除、恢复与永久删除

### Responsibility Member

职责内：

- 删除到回收站：允许；
- 恢复：允许；
- 永久删除：不由 Member 身份授予。

职责外：

- 不因内部成员身份获得删除、恢复或永久删除权。

### Responsibility Lead

职责内：

- 删除到回收站：允许；
- 恢复：允许；
- 永久删除：允许。

多职责对象继续执行第 5 节“权限集合相加”规则，不把一个职责的永久删除权限自动扩散成另一个职责的治理权限。

## 9. 导出与分享

### 9.1 导出

普通职责 Member 可以直接导出本人职责范围内的数据。

### 9.2 内部分享

普通职责 Member 与 Lead 均允许内部分享。

内部分享不产生新的外部访问权，接收者仍按自身已有项目权限访问。

### 9.3 Lead 对外分享

Lead 可以直接对外分享自己职责范围内的内容。

### 9.4 扩大分享

Lead 需要分享超出本人职责范围的内容时必须审批。

扩大分享由 Project Admin 审批。

批准只增加明确批准的分享范围，不自动增加编辑、删除、永久删除、审批或其他不存在的权限。

---

## 10. 审批与编辑分离

拥有编辑权不等于拥有审批权。

拥有审批权也不等于获得正文编辑权。

例如同一职责的 Member 可以创建、修改并提交职责内容，但不会因为可以编辑而自动拥有 Lead 的审批动作。

Client Reviewer 的批准/驳回也不授予其内部生产内容编辑权。

---

## 11. 联系方式

用户注册时提供工作邮箱和工作电话。

内部 Project Member 默认可以查看项目内部成员的工作邮箱和工作电话。

以下外部身份默认不得查看内部成员工作邮箱和电话：

- Client Reviewer；
- Guest；
- Share Visitor；
- 其他仅通过外部分享访问项目内容的身份。

---

## 12. Talent

Talent 不按普通内部 Project Member 的完整项目可见规则处理。

Talent 默认范围为本人相关：

- Character / Casting 关系；
- 本人相关 Scene；
- 本人相关 Shot；
- 本人拍摄信息；
- 本人 Call Sheet；
- 本人准备要求；
- 项目要求本人提交或确认的资料。

不因 Talent 身份开放完整内部项目、内部成员工作联系方式或内部生产信息。

---

## 13. Client Reviewer

Reviewer 与客户合并为 Client Reviewer。

默认可以：

- 查看明确对其开放的审阅内容；
- 查看明确对其开放的交付内容；
- 评论；
- 批准；
- 驳回；
- 要求修改。

默认不得查看：

- 内部项目成员工作电话；
- 内部项目成员工作邮箱；
- 内部项目成员目录；
- 未对其开放的生产信息；
- 未对其开放的素材；
- 内部权限设置。

## 14. 139 个项目岗位如何进入权限系统

139 个岗位的编号、名称、制作分工和职责边界保持现有岗位目录原文。

岗位本身不产生 Team Admin、Agency Admin、System Admin 或 Project Admin 身份。

项目岗位只用于确定：

1. 用户在项目中承担哪些职责；
2. 哪些内容属于其职责内可创建/编辑范围；
3. 是否叠加该岗位对应的职责治理动作；
4. 多岗位时把各岗位已经存在的动作权限相加。

本文件不新增新的岗位、不删除岗位、不合并岗位，也不改变原岗位职责。

## 15. A–H 模块映射只限定职责落点

A–H 模块映射不是权限扩张规则。

例如 D 类岗位模块落点包含摄影、灯光、录音、现场、素材等，但某个具体 D 类岗位只能编辑其岗位职责边界直接对应的内容。

“属于同一大类”不代表可以互相编辑其他岗位职责。

同理：

- 摄影师不会因为属于 D 类而自动获得灯光职责；
- 灯光师不会因为对象同时有 Camera + Lighting 就自动得到 Camera Lead 权限；
- 剪辑师不会因为属于 H 类而自动得到调色、混音、交付等全部 H 类职责。

## 16. 权限计算伪规则

```text
effective_actions =
organization_grants
∪ project_admin_grants
∪ responsibility_A_grants
∪ responsibility_B_grants
∪ ...
∪ approved_cross_responsibility_grants
```

必须满足：

```text
不存在的权限不能因为：

- “最大权限”
- 同对象包含多个职责
```

每一项最终有效动作都应能说明：

```text
谁
因为哪个身份/岗位/职责/审批
在什么范围
获得了什么动作
```

## 20. 岗位拓扑

### 20.1 拓扑规则

岗位拓扑只表达现有岗位在 FrameForge 中所属的职责路径，不建立新的部门、汇报线或岗位。

```text
组织治理身份
├── System Admin
├── Agency Admin
├── Team Admin
└── Project Admin

项目专业岗位
└── A–H 现有工种大类
    └── 现有职责节点
        └── 现有139个岗位
            ├── Lead
            ├── Member
            └── Talent
```

- **Lead**：岗位本身承担其现有职责范围的负责人性质；在职责基础动作之外叠加已经确认的 Lead 治理动作。
- **Member**：普通内部职责岗位；拥有已经确认的职责内基础动作。
- **Talent**：按已经确认的本人相关范围访问，不套用普通内部 Project Member 的完整项目查看规则。
- 上述节点类型不改变岗位原名称、原编号、原制作分工和原职责正文。
- 拓扑父节点不向子节点自动生成新权限；权限仍按岗位本身已有职责计算。
- 一人多岗位时，各岗位权限集合相加；不得按“更高节点”“最高级别”把某个岗位的治理权限传播给其他岗位。
